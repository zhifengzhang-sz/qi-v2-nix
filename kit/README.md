# The kit: a project's spec of its agents, and each kind's files from it (2026-10-16)

A project's `agents/` is its spec of the work agents do on it, in no tool's terms: the rules, the roles and the processes' stages; the record of a run is the format's, the same in every project. Each kind of agent (Claude Code, Copilot, ...) gets its own files from it, generated by the kit; the generated files are built output, never edited, ignored by git. This file is the format, the same in every project, and the kit that reads it. The kit is a flake of its own, `kit/` in the public repository `qi-v2-nix` (first `dev/kit/` in the material's repository, 2026-10-16; moved here 2026-10-21), self-contained (its packages `zod` and `yaml` only); a project takes it as an input of its flake, pinned by its lock, and `make install` links it at `dev/agents`, read-only; the project holds only its own `agents/`. The notes on the kinds: `notes/copilot.md` (Copilot's CLI, cloud agent and VS Code, from their documentation, with what was tried) and `notes/copilot-vscode.md` (VS Code's Local harness, written by Copilot in the owner's VS Code, 2026-10-16).

## The kit

- `kit check [--root DIR]`: decodes the project's `agents/` (`src/spec.ts` is the format's one schema) and writes nothing.
- `kit generate [--kind claude-code|copilot|all] [--root DIR]`: writes each kind's files from it (default `all`: every kind's files, so a developer can switch kinds with nothing stale). Each file is marked generated; `agents.generated` lists them, so a file no longer generated (a role renamed) is removed. The generated files are ignored by git.
- `agents.local.json` (the developer's own, ignored by git): `{"copilot": {"models": {"strongest": "<a full ID of their plan>", ...}}}`; a class with no ID gives a Copilot file with no `model`, the session's then used.
- `kit run-start --role R` and `kit run-check --role R [--files a,b]`: a role's run checked on its output, where a kind cannot restrict its tools (Copilot in VS Code gave `reviewer` edit and shell tools: `notes/copilot-vscode.md`, 4a). Before the run, HEAD, the stash and every path git lists as differing from HEAD in the work tree or the index are recorded (a file by its hash, a link by its target; renames as their two paths; `agents.run/<role>.json`, ignored by git), so a run that commits, stashes, moves or deletes is seen; `--files` takes exact paths, comma-separated; after it, what changed is judged by the role's `writes`: `none`, nothing may change; `brief-files`, only the files named; a role that builds or makes the change, what changed is listed. Files ignored by git are not seen: what a build writes there is the build's. Two roles run at once cannot be told apart.
- `kit hook start|stop`: the check run by the Copilot CLI's hooks, `.github/hooks/kit.json`, which `kit generate` writes with the Copilot files: on `subagentStart` and `subagentStop` the CLI hands the hook a JSON object whose `agentName` is the role's name and `agentId` its run's (`notes/copilot.md`, Tried in the CLI, the payload). The run is recorded under its id on start and judged on stop, as by hand, except a `brief-files` role, whose changes are listed and not judged (a hook does not know the brief). On a role's stop, the hook also writes its validated staging record, `agents.run/<agentId>.run.json`, and the response it names. It records the role, Copilot kind, effort, role brief and changed paths; the hook payload does not give the resolved model, family or token count, so those are explicitly `not reported` until the session supplies `/usage` or OpenTelemetry evidence before attaching the record to a ledger run. Every outcome is a line in `agents.run/log`: the time, the run's id, start or stop, a status word (`RECORDED`, `PASS`, `FAIL`, `LISTED`, `SKIPPED` for a subagent that is no role, `ERROR` for an input or a spec it could not read), then the lines; the hook exits 0 whatever happened, so it never stops the CLI. Two runs at once keep their own records, but their changes mix, the work tree being one. The CLI loads the hooks only in a trusted folder, once `make agents` has written them.
- In the project: `make agents` runs `kit generate`; `make run-start` and `make run-check` the two above.

## What `agents/` holds

| Path | Holds | Generated into (Claude Code; Copilot) |
|---|---|---|
| `rules.md` | the project's own standing rules, two sections: **The session** (whoever drives the work, of any kind) and **Every role** (every agent a role runs as); the rules shared by every project are the kit's (`src/rules.md`, the package's `rules.md`), and a project rule that repeats one of them word for word is refused | `AGENTS.md` (the rules: in each section the kit's shared rules first, then the project's own) and `CLAUDE.md` (a pointer to `AGENTS.md`); the section Every role, the kit's and the project's, also into each role's file |
| `roles/<role>.md` | one role, self-contained: front matter, then its brief | `.claude/agents/<role>.md`; `.github/agents/<role>.agent.md` |
| `stages/<process>.json` | one process's stages | `.claude/workflows/<process>.js`; for Copilot, by hand in order (its workflows are a preview) |

A role's generated file carries a copy of its role and of Every role, so that an agent of a kind that gives a subagent no repository instructions (Copilot, unless `include-custom-instructions`) still has them; the copy is built output, not a second home.

## A role

Front matter in YAML, the facts a binding needs, in words of no tool; then the brief in Markdown, the sections **Reads**, **Changes**, **Runs**, **How it works**, **Report**, **Recorded as**.

```yaml
name: reviewer            # the file's name without .md
for: tries to refute another's work: a document, a proof, code, a finding   # one line; the binding's description
model: strongest          # small | middle | strongest | other
effort: high              # low | medium | high
can: [read, search]       # of read, search, edit, execute, web
writes: none              # none | brief-files | the-change
builds: false             # true: it builds, and takes the project's build lock
```

- **model**: *small*, a cheap model for mechanical work (run, copy, count); *middle*, for gathering and drafting from files; *strongest*, for a review that must refute and a hard proof.
- **other**: the other model, which reads what the others wrote: not the writers' model, of another family where the kind offers one (self-preference, arXiv 2404.13076; preference leakage, arXiv 2502.01534, where relatedness is "same model, inheritance, or same family"). A role is given it at the call when it is the other model (`reviewer`); the run records the model and family, and a run whose kind offers no other family says so.
- **can**: Copilot's own aliases; each kind maps them to its tools.
- **writes** and **builds**: what a kind cannot enforce is checked on the output: `writes: none`, no file edited by the role: `git status` unchanged by the run, or, for a role that builds, changed only by what its targets write (it reports `git status --short`); `brief-files`, only the files the brief names changed; `builds: true`, the Makefile's lock, so two builders never meet.

The kit's mapping, per kind (draft):

| | Claude Code | Copilot (CLI) |
|---|---|---|
| small, middle, strongest | `haiku`, `sonnet`, `opus` | full IDs from the developer's own catalogue, chosen at setup (`claude-opus-5.5` was not offered in one VS Code, 2026-10-16; `notes/copilot.md`, Tried), never an alias: `opus` fails with no fallback |
| other | `fable` | another family's strongest, by its full ID in the plan's catalogue (`gpt-5.4`) |
| effort | `effort` | `reasoningEffort` |
| read, search, edit, execute, web | `Read`; `Grep, Glob`; `Edit, Write`; `Bash`; `WebSearch, WebFetch` | `read`, `search`, `edit`, `execute`, `web` |
| the brief | the file's body | the file's body, with `include-custom-instructions: false` (Every role is in it) |

## A process's stages

`stages/<process>.json`, one object, its `name` the file's:

- `name`, `for`, `when` (when it is run), `doc` (the file that describes the process);
- `params`: each with its `default` and `for` (one line); a model param's default is `{model: <class>}`;
- `order`: the stages run by default, in order, each name a stage's, a stage named again when it runs again; a caller may pass another list (Recheck, Cut, Occur and Screen of `materials` are run so), in which a name with no stage is skipped and logged `unknown stage <name>; skipped`;
- `results`: the shapes the agents return, each field `{type: string|integer|boolean, for}`; `run` is required, the shape of a run's return: `lines` string, `pass` boolean, `count` integer;
- `stages`, each named once, with `name`, `title`, `detail` and one or both of:
  - `run`: commands, run from the root in order (by a small model at low effort, or by hand), with `count` (the number to read from their output) and, where the output names parts, `parts` (a pattern with two groups, the first and the last part, both included);
  - `task`: the brief of one agent, each of its `{placeholders}` (`{n:02}`, zero-padded) bound by `over`, with `result` (one of `results`) and either `role` (a role of `roles/`) or `model` (a param's name, `{model: <class>}`, or `session`: the model of the session that runs the process) with `can` and `writes` as a role's;
  - `over` (with a task): `{each: <a param whose default is a list>, as}`, `{ranges: {count: <a stage with a run>, size}, as: [a, b], index: k}` (ranges of `size` over that stage's last count, `k` from 1), or `{parts: <a stage with parts>, as}`; with none, one agent; a count of 0 gives no agents;
  - `mode`: `parallel`, or `sequential` with `why-sequential` (they edit one file);
  - `then`: `{run, count}`, run after the agents;
  - `stop-if` `{when, log}`: stops the process and logs the line; `skip-if` `{when, record}`: skips the stage's agents and `then`, and records why. `when` is one of `run failed` (the stage has a run), `then failed` (the stage has a `then`; stop-if only), `no parts` (the stage has `parts`), `count of <a stage with a run> is 0`;
  - `missing`: the line logged when some agents return nothing, `{m}` their number.

The order within a stage: its run; its `stop-if` (unless `then failed`) and `skip-if`; its agents; its `then`; its `stop-if` `then failed`. A stage with no `stop-if` goes on whatever its run's exit (`grep -c` exits 1 when it counts 0). `kit check` refuses a spec that breaks any of this.

The process returns its record to its caller: per stage, what each agent returned and each run printed; the session keeps it where the project keeps its reports. Every role (`rules.md`) holds for a stage's agents as for a role's. In Claude Code, a stage's agent with no `role` is a general agent with every tool: its `can` and `writes` are checked on the output, as a role's that a kind cannot enforce.

## A run's record

The record of one agent's run in a role, of any kind; its schema is the kit's (JSON, a Zod schema):

```json
{ "role": "reviewer", "kind": "claude-code", "model": "<as resolved>", "family": "<the model's family>",
  "effort": "high", "tokens": 12345, "tokens_why": "",
  "brief": "<path or digest>", "report": "<path or digest>", "changed": ["<path>"] }
```

`tokens` is a number or `"not reported"`, with `tokens_why` saying why (Copilot gives tokens per model only by `/usage` or OpenTelemetry). It is the agent's half of a run's provenance (who, with what model and family, at what cost); a project records it where its runs are recorded.
